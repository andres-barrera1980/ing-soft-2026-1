02 / 08 — Definición

¿Qué es el patrón Iterator?

"Proporciona una manera de acceder secuencialmente a los elementos de una colección sin exponer su representación interna."

— Gamma, Helm, Johnson, Vlissides (Gang of Four)

¿Qué hace exactamente?

Permite recorrer una lista, árbol o cualquier colección usando siempre los mismos métodos: siguiente() y hayMás(). No importa cómo esté guardada la información internamente — el código que la consume nunca cambia.

¿Por qué es de "comportamiento"?

Porque define cómo se comporta el recorrido de una colección, separando esa responsabilidad del objeto que guarda los datos. La colección guarda, el iterador recorre — cada uno hace una sola cosa.

03 / 08 — El Problema

El problema que resuelve

Imagina que tienes una playlist de canciones. Puedes guardarla de distintas formas, y cada una se recorre de manera diferente:

[ ] Lista / Array Se recorre con un índice numérico: lista[0], lista[1]... Hay que saber cuántos elementos tiene.
🌲 Árbol Hay que usar recursividad para visitar cada rama y hoja. La lógica es completamente diferente.
🗄️ Base de Datos Se necesita una consulta SQL y un cursor especial. Nada que ver con las opciones anteriores.

⚠ Sin Iterator...

Necesitas escribir código diferente para recorrer cada tipo de colección. Si la estructura cambia, tienes que cambiar TODO el código que la recorre. Frágil y difícil de mantener.

✓ Con Iterator...

Siempre usas los mismos métodos: siguiente() y hayMás(). No importa si por dentro es una lista, un árbol o una BD. El código cliente nunca cambia.

04 / 08 — Estructura

Los 4 componentes del patrón

1

Iterador (interfaz)

Iterator

Define los métodos que todo iterador debe tener: siguiente() devuelve el próximo elemento, y hayMás() dice si quedan elementos. Es un contrato que todos los iteradores deben cumplir.

2

Iterador Concreto

ConcreteIterator

Implementa la lógica real de recorrido para una colección específica. Lleva la cuenta de en qué posición va y sabe cómo avanzar al siguiente elemento sin que nadie externo lo sepa.

3

Colección (interfaz)

Aggregate

Define que toda colección debe poder crear su propio iterador mediante el método crearIterador(). Es también un contrato, esta vez para las colecciones — garantiza que siempre haya un iterador disponible.

4

Colección Concreta

ConcreteAggregate

Es la colección real: una lista de canciones, un árbol de archivos, etc. Sabe cómo crear el iterador adecuado para recorrerse a sí misma, y lo entrega cuando se le pide.

05 / 08 — Implementación

Ejemplo en código — Java

import java.util.List;

class IteratorLista {
  private List<String> canciones;
  private int pos;

  public IteratorLista(List<String> canciones) {
    // Guarda la lista, empieza en posición 0
    this.canciones = canciones;
    this.pos = 0;
  }

  public boolean hayMas() {
    // ¿Quedan elementos por recorrer?
    return pos < canciones.size();
  }

  public String siguiente() {
    // Devuelve el actual y avanza la posición
    return canciones.get(pos++);
  }
}

// ── Uso ──────────────────────────
List<String> canciones = List.of(
    "Hotel California",
    "Bohemian Rhapsody",
    "Stairway to Heaven"
);
IteratorLista it = new IteratorLista(canciones);

while (it.hayMas()) {
    System.out.println(it.siguiente());
}

// Hotel California
// Bohemian Rhapsody
// Stairway to Heaven

Constructor IteratorLista()

Recibe la lista de canciones y guarda un contador en cero. Ese contador es la "posición actual" del iterador — es lo único que necesita recordar.

Método hayMas()

Compara la posición actual con el tamaño total de la lista usando size(). Si la posición no ha llegado al final, devuelve true y el bucle continúa.

Método siguiente()

Usa get(pos++) para devolver el elemento en la posición actual y avanzar el contador en un solo paso. Así siempre avanza hacia adelante.

Cómo se usa

Un while con hayMas() y siguiente() recorre toda la colección de forma limpia, sin necesitar índices ni conocer el tamaño.

06 / 08 — Evaluación

Ventajas y desventajas

✓ Ventajas
Oculta la complejidad interna

El código que usa la colección no necesita saber si es un array, un árbol o una base de datos. Solo llama a siguiente() y listo.

Responsabilidad única

La colección se encarga de guardar datos y el iterador se encarga de recorrerlos. Cada uno hace solo una cosa — principio SOLID cumplido.

Varios recorridos simultáneos

Puedes tener dos o más iteradores sobre la misma colección al mismo tiempo, cada uno en una posición distinta e independiente.

Fácil de cambiar la colección

Si cambias la estructura interna (de lista a árbol, por ejemplo), el código que la recorre no necesita modificarse.

✗ Desventajas
Puede ser excesivo para casos simples

Si solo tienes una lista pequeña que siempre recorres de la misma forma, crear un iterador aparte añade código innecesario sin beneficio real.

Acceso más lento que por índice

Acceder a lista[5] directamente es más rápido que llamar a siguiente() cinco veces. En colecciones muy grandes puede notarse.

Más clases en el proyecto

Necesitas crear al menos dos clases nuevas (la interfaz y el iterador concreto), lo que aumenta la cantidad de archivos a mantener.

07 / 08 — Aplicaciones

¿Dónde se usa en la vida real?

🎵 Reproductores de música

Recorren la playlist sin importar si está en memoria, en caché o cargada desde internet. La interfaz de reproducción es siempre la misma.

🌐 Historial del navegador

Navegar atrás y adelante entre páginas visitadas con los mismos botones, sin importar cómo se almacena el historial internamente.

📁 Explorador de archivos

Listar archivos y carpetas con la misma interfaz sin importar si el sistema operativo es Windows, Mac o Linux.

🛒 Carrito de compras

Recorrer todos los productos del carrito para calcular el total o mostrar el resumen sin saber cómo están almacenados.

📊 Reportes empresariales

Iterar sobre filas de una BD, un CSV o una API con exactamente la misma lógica de negocio sin modificar el código.

🎮 Videojuegos

Recorrer enemigos activos, items del inventario o casillas del mapa con una interfaz unificada independiente de la estructura interna.

08 / 08 — Conclusión

Conclusión

El patrón Iterator resuelve un problema simple y universal: necesito recorrer elementos, pero no quiero depender de cómo están guardados. Cuatro ideas clave para recordar:

01
Interfaz uniforme: siempre los mismos métodos — siguiente() y hayMás() — sin importar qué tipo de colección hay por debajo.
02
Encapsulamiento: la colección NO expone su estructura interna. El cliente no necesita saber si es un array, árbol o base de datos.
03
Ya lo usas: el for/foreach de Python, Java y JavaScript ES el patrón Iterator implementado por el lenguaje.
