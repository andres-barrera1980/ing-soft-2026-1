PATRONES DE DISEÑO · GOF · ESTRUCTURAL DE OBJETO

DECORATOR

Adjunta responsabilidades adicionales a un objeto de forma dinámica. Alternativa flexible a la herencia para extender funcionalidad.

También: Wrapper Tipo: Estructural Scope: Object GoF — Gamma et al.
01 — INTENCIÓN

¿Qué es el Decorator?

Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

¿Qué hace?
  • Envuelve un objeto en otro que extiende su comportamiento
  • El decorador conforma la misma interfaz del componente que decora
  • Su presencia es transparente para los clientes
  • Se pueden anidar múltiples decoradores recursivamente
  • El decorador reenvía las solicitudes al componente original
¿Cuándo usarlo?
  • Para añadir responsabilidades a objetos individuales de forma dinámica y transparente
  • Cuando las responsabilidades deben poder retirarse
  • Cuando la extensión por subclases es impráctica
  • Cuando un gran número de extensiones independientes produciría una explosión de subclases
  • Cuando la definición de una clase está oculta o no disponible para subclasificar
02 — MOTIVACIÓN

El Problema a resolver

❌  Con Herencia
  • TextView
  •   ScrollableTextView
  •   BorderedTextView
  •   BorderedScrollableTextView
  •   DropShadowTextView
  •   BorderedDropShadowScrollableTextView
  •   ... ∞

  • Explosión de subclases para cada combinación
  • Elección estática en tiempo de compilación
  • Inflexible: no se puede cambiar en tiempo de ejecución
  • El cliente no controla cómo ni cuándo decorar
  • Herencia múltiple de la misma clase es propensa a errores
✓  Con Decorator
new BorderDecorator(
  new ScrollDecorator(
    new TextView()
  )
)
  • Composición dinámica en tiempo de ejecución
  • Una sola clase base limpia (TextView)
  • Combinaciones ilimitadas sin nuevas clases
  • Se puede añadir una propiedad dos veces fácilmente
  • Transparente para el cliente: misma interfaz

Herencia (triángulo △)

ConcreteComponent y Decorator heredan de Component. Esto garantiza que los decoradores puedan usarse en cualquier lugar donde se espere un Component.

Composición (◆ component)

Decorator mantiene una referencia al Component que decora. El método Operation() reenvía la llamada al componente y puede añadir comportamiento antes o después.

04 — PARTICIPANTES

Roles del Patrón

01
Component
Ej: VisualComponent

Define la interfaz para objetos que pueden tener responsabilidades añadidas dinámicamente. Es la interfaz común que deben implementar tanto el componente concreto como el decorador, garantizando la transparencia.

02
ConcreteComponent
Ej: TextView

Define un objeto al que se le pueden adjuntar responsabilidades adicionales. Es el objeto "núcleo" que será decorado. Implementa la interfaz Component sin adornos extra.

03
Decorator
Ej: Decorator (clase abstracta)

Mantiene una referencia a un objeto Component y define una interfaz que conforma la interfaz de Component. Delega las operaciones al componente envuelto. Puede ser concreto si solo se necesita un decorador.

04
ConcreteDecorator
Ej: ScrollDecorator, BorderDecorator

Añade responsabilidades concretas al componente. Extiende el comportamiento de Decorator sobreescribiendo Operation() para ejecutar acciones adicionales antes y/o después de delegar al componente.

05 — IMPLEMENTACIÓN EN JAVA

Código Java paso a paso

Beverage.java — Interfaz Component
// 1. La interfaz base (Component)
public interface Beverage {
    String getDescription();
    double cost();
}
DarkRoast.java — ConcreteComponent
// 2. El componente concreto
public class DarkRoast
    implements Beverage {

    public String getDescription() {
        return "Dark Roast Coffee";
    }

    public double cost() {
        return 0.99;
    }
}
CondimentDecorator.java — Decorator abstracto
// 3. La clase Decorator abstracta
public abstract class CondimentDecorator
    implements Beverage {

    protected Beverage beverage;
    // Delegación explícita
}
Mocha.java — ConcreteDecorator
// 4. Un decorador concreto
public class Mocha
    extends CondimentDecorator {

    public Mocha(Beverage b) {
        this.beverage = b;
    }

    public String getDescription() {
        return beverage.getDescription()
            + ", Mocha";
    }

    public double cost() {
        return 0.20 + beverage.cost();
    }
}
06 — EJEMPLO DE USO

Decoradores en acción

Main.java — Composición dinámica
// Café base sin adornos
Beverage bev = new DarkRoast();
// → "Dark Roast Coffee"  $0.99

// Envolver con un Mocha
bev = new Mocha(bev);
// → "Dark Roast Coffee, Mocha"  $1.19

// Añadir un segundo Mocha
bev = new Mocha(bev);
// → "Dark Roast Coffee, Mocha, Mocha"  $1.39

// Añadir crema batida
bev = new Whip(bev);
// → "Dark Roast Coffee, Mocha, Mocha, Whip"

System.out.println(bev.getDescription());
// "Dark Roast Coffee, Mocha, Mocha, Whip"

System.out.println(bev.cost());
// 1.49
☕ Composición dinámica

Cada new Mocha(bev) envuelve al objeto anterior, añadiendo su propio costo y descripción. El objeto resultante se comporta como un todo unificado.

🔗 Interfaz uniforme

El cliente siempre llama .getDescription() y .cost() sobre el mismo tipo Beverage, sin importar cuántos decoradores estén apilados.

🔄 Repetición sin errores

Aplicar Mocha dos veces es trivial y correcto. Con herencia, heredar de Border dos veces es propenso a errores en C++ y directamente ilegal en Java.

🧮 Cadena de responsabilidad

La llamada a cost() se propaga recursivamente: Whip → Mocha → Mocha → DarkRoast, acumulando el valor en cada nivel: 0.10 + 0.20 + 0.20 + 0.99 = 1.49

07 — CONSECUENCIAS POSITIVAS

Ventajas del Patrón

⚡
Más flexibilidad que la herencia estática

Las responsabilidades se añaden y eliminan en tiempo de ejecución simplemente adjuntando y desvinculando decoradores. La herencia, en contraste, exige crear una nueva clase para cada responsabilidad adicional (ej: BorderedScrollableTextView), lo que aumenta exponencialmente la complejidad.

🧩
Principio Abierto/Cerrado (OCP)

Las clases están abiertas para extensión pero cerradas para modificación. No es necesario modificar el código existente para añadir nueva funcionalidad. Cada decorador es independiente y puede desarrollarse por separado.

💡
Evita clases sobrecargadas (pay-as-you-go)

En lugar de intentar soportar todas las funciones posibles en una clase compleja, se define una clase simple y se añade funcionalidad incrementalmente con decoradores. La aplicación no paga por características que no usa. Extender una clase compleja tiende a exponer detalles no relacionados.

🔁
Repetición limpia de responsabilidades

Es trivial añadir una propiedad dos veces: para doble borde, simplemente se aplican dos BorderDecorator. Con herencia, heredar de Border dos veces es propenso a errores (en C++) o directamente inválido (en Java).

🔀
Mezcla y combinación de responsabilidades

Proveer diferentes clases Decorator para un Component específico permite combinar responsabilidades de formas que serían imposibles o muy costosas con herencia múltiple.

🔒
Transparencia para el cliente

Los decoradores implementan la misma interfaz que el componente. Los clientes no pueden (ni necesitan) distinguir entre un componente decorado y uno sin decorar, lo que elimina la dependencia en la decoración.

08 — CONSECUENCIAS NEGATIVAS

Desventajas y Limitaciones

⚠️
No son idénticos al componente

Un decorador actúa como enclosure transparente, pero desde el punto de vista de identidad de objeto (== o instanceof), un componente decorado no es idéntico al componente en sí. No se debe confiar en la identidad del objeto cuando se usan decoradores.

🔩
Muchos objetos pequeños

Un diseño con Decorator suele resultar en sistemas compuestos por muchos objetos pequeños que se parecen entre sí. Aunque son fáciles de personalizar para quienes los entienden, pueden ser difíciles de aprender y depurar para quienes no.

🔍
El orden de composición importa

El orden en que se anidan los decoradores puede cambiar el resultado final. Un error en el orden de composición puede producir comportamientos sutiles y difíciles de detectar. Requiere documentación cuidadosa del orden esperado.

📐
Problemas con verificación de tipo

Si el código cliente necesita verificar el tipo concreto del componente (instanceof), el decorador rompe ese chequeo ya que el objeto externo es el decorador, no el componente. Requiere diseño cuidadoso de la API.

🐛
Difícil de depurar

Al tener múltiples capas de objetos anidados, los stack traces en depuración pueden volverse profundos y difíciles de seguir. Los errores en un nivel intermedio de la cadena pueden ser complicados de localizar.

⚖️
No apto para componentes pesados

Si la clase Component es intrínsecamente pesada, el Decorator puede ser demasiado costoso de aplicar en cantidad. En ese caso, el patrón Strategy es una mejor alternativa, permitiendo cambiar el comportamiento sin la sobrecarga del anidamiento.

09 — CASO REAL

Decorator en Java I/O

Java usa el patrón Decorator internamente en su librería java.io. Las clases de streams están diseñadas exactamente según este patrón, permitiendo combinar distintas capacidades de forma flexible.

aStream->PutString("aString");
InputStream (abstracto)

Clase base — el Component del patrón. Define la interfaz read().

FilterInputStream

El Decorator abstracto. Todos los decoradores de I/O heredan de aquí.

Buffered / Data / Cipher

Los ConcreteDecorators. Cada uno añade una capa de funcionalidad: buffer, tipos, cifrado.

10 — PATRONES RELACIONADOS

Comparativa con otros Patrones

🔌
Adapter (p.139)
Decorator vs Adapter
Un Adapter cambia la interfaz de un objeto por completo, dándole una interfaz totalmente nueva. Un Decorator solo añade responsabilidades manteniendo exactamente la misma interfaz del componente original. La presencia del Decorator es completamente transparente para los clientes.
🌳
Composite (p.163)
Decorator vs Composite
Un Decorator puede verse como un Composite degenerado con un solo componente (en lugar de varios hijos). Sin embargo, un Decorator añade responsabilidades adicionales — no está pensado para la agregación de objetos. Composite enfoca en la estructura jerárquica; Decorator en el enriquecimiento de comportamiento.
🧠
Strategy (p.315)
Decorator vs Strategy
Decorator cambia la "piel" del objeto desde afuera — el componente no sabe nada de sus decoradores. Strategy cambia las "tripas" — el componente delega parte de su comportamiento a un objeto estrategia que conoce. Strategy es preferible cuando el Component es intrínsecamente pesado (costoso de decorar). Estas son dos alternativas para cambiar dinámicamente el comportamiento de un objeto.
11 — CONCLUSIÓN

Lo que hay que recordar

"Envuelve objetos para extender su comportamiento en tiempo de ejecución, sin tocar el código original."
  • ✓ Alternativa flexible a la herencia — evita la explosión de subclases para cada combinación de funciones
  • ✓ Composición dinámica en tiempo de ejecución, no estática en tiempo de compilación
  • ✓ Aplica el Principio Abierto/Cerrado con elegancia y sin modificar código existente
  • ✓ Omnipresente en Java I/O (InputStream), frameworks y librerías modernas
  • ✓ El decorador es transparente — misma interfaz, mismos métodos, mismos contratos
  • ⚠ Cuidado: el orden de composición importa y muchos objetos pequeños dificultan el debug
  • ⚠ No usar cuando se requiera verificación de identidad (instanceof) del componente interno
