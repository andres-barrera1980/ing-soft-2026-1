Motivación

El Problema:
Alto Acoplamiento

Font Chooser – GoF pág. 274

🕸️

Conexiones N×N

Cuando N objetos se comunican directamente entre sí, se generan hasta N² dependencias. El sistema actúa como un monolito.

🔒

Bajo reúso

Un objeto que conoce muchos otros no puede ser reutilizado sin arrastrar todas sus dependencias.

⚙️

Difícil de cambiar

El comportamiento está repartido entre muchas clases. Cualquier cambio obliga a modificar múltiples subclases.

💡

Ejemplo del libro

Un diálogo GUI: botones, listas y campos de texto se afectan mutuamente. Cada widget conoce a todos los demás.

02 / 07
Intención & Propósito

¿Qué define el patrón
Mediator?

"Define an object that encapsulates how a set of objects interact. Mediator promotes loose coupling by keeping objects from referring to each other explicitly, and it lets you vary their interaction independently." — Gamma et al., Design Patterns, pág. 273
💡 Clave conceptual

Los objetos (Colleagues) dejan de conocerse entre sí: solo conocen al Mediador. El mediador centraliza y coordina toda la lógica de interacción.

🚦 Analogía

Piensa en el control de tráfico aéreo: los aviones no se hablan entre sí, todos hablan con la torre de control. La torre coordina quién aterriza, quién espera y por dónde. El Mediador es esa torre.

Cuándo aplicarlo

• Un conjunto de objetos se comunica de forma compleja y difícil de entender.
• Reutilizar un objeto es difícil porque referencia a muchos otros.
• El comportamiento distribuido debe ser personalizable sin proliferar subclases.

03 / 07
Estructura del Patrón

Diagrama de Clases

1. Interfaz Mediator

Declara los métodos de comunicación con los componentes. Típicamente incluye un único método de notificación.

2. Concrete Mediator

Encapsula la lógica de comunicación y las relaciones entre los componentes. Conoce y mantiene referencias a los componentes.

3. Componentes (Colleagues)

Clases con lógica de negocio. Tienen una referencia a su mediador y no se comunican con otros componentes directamente.

04 / 07
Ejemplo en Java — Sistema de Chat

Mediator en Práctica

// ── 1. Interfaz Mediator ──────────────────────────────────
interface ChatMediator {
    void sendMessage(String msg, User sender);
    void addUser(User user);
}

// ── 2. ConcreteMediator ───────────────────────────────────
class ChatRoom implements ChatMediator {
    private List<User> users = new ArrayList<>();

    public void addUser(User u)  { users.add(u); }

    public void sendMessage(String msg, User sender) {
        for (User u : users) {
            if (u != sender) u.receive(msg);  // no se conocen entre sí
        }
    }
}

// ── 3. Colleague ──────────────────────────────────────────
class User {
    private final String name;
    private final ChatMediator mediator;  // solo conoce al mediador

    User(String name, ChatMediator m) { this.name = name; mediator = m; }

    public void send(String msg) {
        System.out.println(name + " → [Mediador] → todos: " + msg);
        mediator.sendMessage(msg, this);
    }
    public void receive(String msg) {
        System.out.println(name + " recibió: " + msg);
    }
}

// ── 4. Cliente ────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        ChatMediator sala = new ChatRoom();
        User ana  = new User("Ana",  sala);
        User bob  = new User("Bob",  sala);
        User luis = new User("Luis", sala);
        sala.addUser(ana); sala.addUser(bob); sala.addUser(luis);
        ana.send("¡Hola a todos!");
    }
}
05 / 07
Trade-offs del patrón

Ventajas y Desventajas

✔ Ventajas

  • Elimina dependencias directas entre Colleagues, reduciendo el acoplamiento de N² a N.
  • Favorece el principio de responsabilidad única: la lógica de coordinación vive en un solo lugar.
  • Las clases Colleague son más fáciles de reutilizar de forma independiente.
  • Cambiar el comportamiento de interacción requiere solo cambiar o extender el ConcreteMediator.
  • Relaciones many-to-many se convierten en one-to-many (más fáciles de mantener).

✗ Desventajas

  • El Mediator puede convertirse en un God Object: un monolito que concentra demasiada lógica.
  • A medida que crece el sistema, el Mediator se vuelve complejo y difícil de mantener.
  • Puede ser overkill en sistemas con pocas interacciones entre objetos.
  • La depuración puede ser más difícil porque el flujo de control es menos obvio.
