Active Record

El puente entre la Lógica de Dominio y la Persistencia de Datos.

Origen y Autoría

Propuesto formalmente por Martin Fowler en su libro seminal de 2003:

"Patterns of Enterprise Application Architecture" (PEAA)

Fowler identificó este patrón al observar cómo los desarrolladores integraban bases de datos SQL en lenguajes orientados a objetos de forma rápida y efectiva.

CONTEXTO HISTÓRICO:

Surgió como una alternativa potente a los complejos EJB (Enterprise JavaBeans) de la época, priorizando la simplicidad y la cohesión.

02 / 12

¿Qué es exactamente?

"Un objeto que envuelve una fila en una tabla o vista de base de datos, encapsula el acceso a la base de datos y añade lógica de dominio sobre esos datos."

Diagrama: Isomorfismo Active Record

TABLA SQL

IDNAMESTATUS
1Juanactive

── fila → objeto ──

→

ACTIVE RECORD: Customer

DATOS: id, name, status

PERSISTENCIA: find(), insert(), update()

LÓGICA: isPremium(), calcularDescuento()

En Active Record, los datos y el comportamiento viven juntos. No hay una separación estricta entre "el que guarda" y "lo que se guarda".

03 / 12

Los 6 Métodos Estándar

Según el libro PEAA, una clase Active Record típica debe implementar:

  • 1. Constructor (de fila SQL): Crea instancia desde un ResultSet.
  • 2. Constructor (de inserción): Prepara un objeto nuevo vacío.
  • 3. Finders Estáticos: Encapsulan SELECTs (ej. findBy(id)).
  • 4. Persistence Methods: Métodos de instancia para INSERT/UPDATE.
  • 5. Data Accessors: Getters y Setters para cada columna.
  • 6. Domain Logic: La "corteza" del negocio sobre los datos.

Active Record en Java

Implementación de los 6 métodos estándar en la clase Customer:

public class Customer {
    private int id;
    private String name;
    private String status;
    // 1. Constructor desde fila SQL
    public Customer(ResultSet rs) throws SQLException {
        this.id = rs.getInt("id");
        this.name = rs.getString("name");
        this.status = rs.getString("status");
    }
    // 2. Constructor para nuevo registro
    public Customer(String name, String status) {
        this.name = name; this.status = status;
    }
    // 3. Finder estatico
    public static Customer find(int id) {
        String sql = "SELECT * FROM customers WHERE id = ?";
        // ... JDBC query ...
    }
    // 4a. INSERT / 4b. UPDATE
    public Long insert() { /* ... */ }
    public void update() { /* ... */ }
    // 5. Data Accessors
    public String getName() { return name; }
    public void setName(String n) { name = n; }
    // 6. Domain Logic
    public boolean isPremium() {
        return "premium".equals(status);
    }
}

¿Para qué se utiliza?

  • Prototipado Rápido: Cuando el tiempo de mercado es crítico y la lógica no es excesivamente compleja.
  • Aplicaciones centradas en Datos: Sistemas donde la estructura de la aplicación refleja casi perfectamente la base de datos.
  • Validaciones de Registro Único: Operaciones que solo requieren la información de una fila.
  • Evolución de Scripts: Para organizar código que ha crecido demasiado usando el patrón Transaction Script.

EL "SWEET SPOT"

Brilla en aplicaciones CRUD donde las tablas son "objetos de primera clase" y las relaciones no son complejas.

06 / 12

Simetría 1:1 (Isomorfismo)

La regla de oro del diseño en Active Record es la correspondencia exacta entre el código y la persistencia.

SQL TABLE: CUSTOMER

ID: INTEGER
NAME: VARCHAR
STATUS: VARCHAR

↔

CLASS: CUSTOMER

this.id
this.name
this.status

No hay capas de traducción complejas. Lo que ves en la DB es lo que tienes en el objeto.

07 / 12

Ventajas del Patrón

Simplicidad

Es extremadamente intuitivo. Cualquier programador entiende que un usuario tiene un método user.save().

Baja Indirección

No hay que navegar por 5 capas de código para encontrar dónde se guarda un dato.

Productividad Inmediata

Frameworks como Ruby on Rails y Laravel (Eloquent) han demostrado que permite construir aplicaciones en tiempo récord.

08 / 12

El Punto de Quiebre

A medida que la lógica crece, Active Record empieza a mostrar sus debilidades:

  • Acoplamiento Fuerte: El diseño es "esclavo" del esquema de la base de datos.
  • Dificultad de Testing: Difícil probar el negocio sin tocar la base de datos real.
  • Violación del SRP: El objeto tiene dos razones para cambiar (negocio o DB).
  • La Pesadilla de la Herencia: El mapeo 1:1 falla cuando intentas modelar jerarquías de clases complejas.

Relaciones y Concurrencia

Gestión de Relaciones

¿Cómo maneja las claves foráneas?

  • Foreign Key Mapping: El objeto contiene el ID del padre.
  • Lazy Load: Los "hijos" se cargan solo cuando se accede al método, ej: cliente.getPedidos().

Control de Concurrencia

Para evitar colisiones de datos:

  • Optimistic Locking: Uso de una columna version o timestamp.
  • Si el dato cambió en la DB antes de guardar, el objeto lanza una excepción.
